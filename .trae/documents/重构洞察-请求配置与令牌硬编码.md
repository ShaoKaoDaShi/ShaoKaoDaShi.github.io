# 1. 问题

源文件 src/fetch.js 直接在脚本中硬编码了认证令牌与大量环境特定 Header，同时将请求体与输出文件路径写死。这会带来明显的安全风险与跨环境维护困难。

## 1.1. **认证与环境信息硬编码**
- 位置：src/fetch.js 第 3-20 行，包含 `authorization: Bearer ...`、`x-jwt-token`、`x-tt-env`、`x-use-ppe`、`x-bits-auth-appid` 等。
- 问题：
  - 令牌泄露风险高（明文存在于仓库与构建产物）。
  - 令牌到期或变更需改代码，容易遗漏；多环境切换困难。
- 代表性代码：
```js
fetch("https://zhongkui.bytedance.net/api/v1/mrs/7591269/cards_feed", {
  headers: {
    authorization: "Bearer <hard-coded-token>",
    "x-jwt-token": "<hard-coded-jwt>",
    "x-tt-env": "ppe_feat_mr_report",
    "x-use-ppe": "1",
    "x-bits-auth-appid": "112801",
    // ...
  },
  // ...
});
```

## 1.2. **请求体、URL 与输出路径写死**
- 位置：
  - 第 2 行固定 URL 与路径段 `.../mrs/7591269/cards_feed`。
  - 第 22 行 `body` 写死为字符串 `{ "mode": "develop", "tab": "all" }`。
  - 第 24 行输出固定写入 `./data.json`。
- 问题：
  - 脚本只能在单一场景工作，复用性差；无法通过参数或配置灵活切换。
  - 测试与 CI/CD 不易注入不同数据、路径与环境。
- 代表性代码：
```js
"body": "{\"mode\":\"develop\",\"tab\":\"all\"}",
// ...
}).then(res => res.json())
  .then(json => fs.writeFile("./data.json", JSON.stringify(json, null, 2)));
```

## 1.3. **非必要浏览器指纹 Header**
- 位置：第 8-13 行包含 `sec-ch-ua`、`sec-fetch-*`、`sec-ch-ua-platform` 等典型浏览器上下文头。
- 问题：
  - 在 Node 环境中通常不必携带，绑定到特定浏览器版本与平台，增加脆弱性。
  - 真实环境切换（本地/测试/预发/生产）时，这些头值可能导致不可预期的服务端行为或被网关判定为异常。

# 2. 收益

一句话总结：将敏感信息与环境参数提取为配置/环境变量，并封装请求与 IO，使脚本在行为不变的前提下更安全、更可维护。

## 2.1. **降低安全风险**
- 令牌不再出现在代码库与构建产物中，支持密钥轮换与权限收敛。

## 2.2. **提升可维护性与复用性**
- URL、请求体、输出路径可通过配置或参数化控制，减少代码改动点。
- 预计核心脚本的修改点从多处减少到配置集中一处，认知负担显著降低。

## 2.3. **改善跨环境与可测试性**
- 通过 `process.env` 与 `.env`，可轻松在本地/测试/预发/生产间切换。
- 单元测试与集成测试可以注入伪令牌与临时输出目录，更易构造用例与隔离副作用。

# 3. 方案

总体思路：引入配置层与环境变量管理，封装请求构造与文件 IO，默认保持现有行为，移除非必要的浏览器指纹 Header。

## 3.1. **实现步骤**
- 引入 dotenv（或直接使用进程环境）：在项目根创建 `.env`，通过 `process.env` 读取敏感与环境参数。
- 新增轻量配置模块 `src/config.js`：集中校验并暴露所需配置项，避免散落在脚本中。
- 抽取请求客户端 `src/mrsClient.js`：负责构造 headers（只保留必要项）与调用接口，便于复用与测试。
- 参数化请求体与输出路径：支持通过环境变量或函数参数覆盖默认值。
- 移除 `sec-*` 等浏览器指纹头：仅在确有网关要求时，才作为可选配置开启。

## 3.3. **修改后代码示例**
```js
// src/config.js
import dotenv from "dotenv";
dotenv.config();

export const config = {
  MRS_BASE_URL: process.env.MRS_BASE_URL ?? "https://zhongkui.bytedance.net",
  MRS_APP_ID: process.env.MRS_APP_ID ?? "112801",
  MRS_TOKEN: process.env.MRS_TOKEN,           // 对应 Authorization Bearer
  MRS_JWT: process.env.MRS_JWT,               // 对应 x-jwt-token
  TT_ENV: process.env.TT_ENV,                 // 可选：x-tt-env
  USE_PPE: process.env.USE_PPE,               // 可选：x-use-ppe
  CLIENT_LOCALE: process.env.CLIENT_LOCALE ?? "zh",
  OUTPUT_PATH: process.env.OUTPUT_PATH ?? "./data.json",
};

export function buildHeaders(cfg = config) {
  return {
    accept: "application/json",
    "content-type": "application/json",
    ...(cfg.MRS_TOKEN && { authorization: `Bearer ${cfg.MRS_TOKEN}` }),
    ...(cfg.MRS_JWT && { "x-jwt-token": cfg.MRS_JWT }),
    "x-bits-auth-appid": cfg.MRS_APP_ID,
    "x-client-locale": cfg.CLIENT_LOCALE,
    ...(cfg.TT_ENV && { "x-tt-env": cfg.TT_ENV }),
    ...(cfg.USE_PPE && { "x-use-ppe": cfg.USE_PPE }),
  };
}
```
```js
// src/mrsClient.js
import { config, buildHeaders } from "./config.js";
import fs from "fs/promises";

export async function fetchCardsFeed({ mode = "develop", tab = "all" } = {}) {
  const url = `${config.MRS_BASE_URL}/api/v1/mrs/7591269/cards_feed`;
  const res = await fetch(url, {
    method: "POST",
    headers: buildHeaders(config),
    body: JSON.stringify({ mode, tab }),
  });
  const json = await res.json();
  await fs.writeFile(config.OUTPUT_PATH, JSON.stringify(json, null, 2));
  return json;
}

// 入口脚本（可替换 src/fetch.js 的内容）：
fetchCardsFeed();
```
- 说明：
  - 行为保持一致（默认 `mode=develop`，`tab=all`），但所有敏感与环境参数已转为可配置。
  - 仅保留必要 Header，减少对浏览器上下文的依赖。

# 4. 回归范围

本次修改不改变业务行为（仍然调用同一接口并输出 JSON），重点回归在不同环境与配置组合下的脚本稳定性与安全性。

## 4.1. 主链路
- 场景一：本地环境（开发令牌），默认输出路径。
  - 预置：`.env` 包含 `MRS_TOKEN`、`MRS_JWT`、`MRS_BASE_URL`。
  - 步骤：运行脚本，观察是否生成 JSON 文件且内容结构与旧版一致。
- 场景二：测试/预发环境切换。
  - 预置：设置 `TT_ENV` 与 `USE_PPE`，切换不同网关策略。
  - 步骤：运行脚本，确认请求成功、响应无差异，输出路径可通过 `OUTPUT_PATH` 定制。
- 场景三：参数化请求体。
  - 预置：通过函数参数或环境变量覆盖 `mode`、`tab`。
  - 步骤：响应内容按预期变化，写入文件正确。

## 4.2. 边界情况
- 缺失令牌：未设置 `MRS_TOKEN` 或 `MRS_JWT`。
  - 期望：请求被服务端拒绝时，应有明确错误提示；脚本不崩溃，可输出错误日志或退出码。
- 非法令牌或过期：
  - 期望：返回 401/403 时记录原因；便于轮换令牌验证。
- 输出路径不可写：
  - 期望：捕获文件系统异常，提示权限或磁盘问题；不影响后续分析。
- 网络异常或超时：
  - 期望：重试策略（如需要）或明确失败；不产生半成品文件。
- 网关要求特定头：
  - 期望：如确需 `sec-*` 头，可通过配置显式开启并记录来源，避免默默绑定到浏览器版本。
